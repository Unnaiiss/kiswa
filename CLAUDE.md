Project: KISWA — Attar / Perfume Store

Production e-commerce + offline POS billing + unified admin panel. Currency: INR (₹). Market: India. Mobile-first. Backend: Firebase.

Three apps in one Next.js project
Storefront (public, route group (store)): luxury feel, dark + gold theme, smooth Framer Motion animations, fast, SEO-friendly.
POS at /pos (staff login): fast tablet/phone billing screen for the physical shop. Big touch targets, minimal taps per bill.
Admin at /admin (admin login): dashboard, products, stock, sales, reports across BOTH channels.
Inventory model: BULK OIL, not per-variant bottle counts
Every variant of a fragrance (every oil size AND every spray size) is bottled from that fragrance's single shared attar oil pool — there is no independent stock per bottle size. Each product has ONE oilStockMl (decimals allowed) and one lowStockThresholdMl (default 10). Each variant has oilMlPerUnit: how many ml of that shared pool one unit of that variant consumes. Defaults: Oil 3ml=3, Oil 6ml=6, Oil 12ml=12, Spray 20ml=2.4, Spray 50ml=6, Spray 100ml=12 — editable per variant in admin. A variant is purchasable only while oilStockMl >= its oilMlPerUnit; the max qty addable (storefront cart or POS bill) is floor(remaining oilStockMl / oilMlPerUnit), where "remaining" nets out oil already committed to OTHER lines of the same product in that same cart/bill (they all draw from one pool).
Firestore data model
products/{id} (id = slug): name, slug, description, notes (fragrance notes), category, imageUrls[], isActive, oilStockMl, lowStockThresholdMl, variants[] (embedded array: variantId, type ('oil' | 'spray'), sizeMl, priceInr, mrpInr, oilMlPerUnit, isActive), createdAt. `oilStockMl` is the ONLY stock number for the product — it may ONLY be changed inside the recordSale/stockIn/stockAdjust transactions below, never edited directly. Every fragrance has exactly six variants: Oil 3ml/6ml/12ml, Spray 20ml/50ml/100ml.
stockMovements/{id}: productId, productName, variantId (nullable — set only for sale-driven line items, null for product-level Stock In/Adjustment/Set-exact-stock), variantLabel (nullable, snapshot like "Oil 3ml"), mlChange (+/-, ml of oil), reason ('opening_stock' | 'purchase' | 'online_sale' | 'offline_sale' | 'adjustment' | 'return'), referenceId (saleId if any), note, createdAt. Every stock change writes a movement — this is the audit trail.
sales/{id}: channel ('online' | 'offline'), invoiceNo (unique, 'KSW-YYYY-NNNN'), customerName, customerPhone, items[] (embedded array: productId, productName, variantId, sizeMl, unitPrice, qty, lineTotal, oilMlUsed — oilMlPerUnit*qty snapshotted at sale time, since oilMlPerUnit is editable and historical reports must not shift when it changes — plus gifting metadata isGift, giftRecipientName, giftMessage, giftSenderName, giftWrap, all optional/false by default, plus combo metadata comboId, comboTitle, comboComponents (optional — set only for combo lines; see Combo offers below)), subtotal, discount, total, totalOilMlUsed (sum of items[].oilMlUsed, snapshotted), paymentMethod ('razorpay' | 'cash' | 'upi' | 'card'), paymentStatus, razorpayOrderId, razorpayPaymentId, orderStatus ('pending' | 'paid' | 'packed' | 'shipped' | 'delivered' | 'cancelled'), shippingAddress (map, online only), createdByUid, createdAt, giftShippingAddress (optional map — line1/line2/city/state/pincode/country plus name/phone for the recipient; set only when a gift item's "deliver to a different address" was chosen at checkout), hidePrices (optional bool, default false — "hide prices in the package" packing instruction, not a technical price-hiding mechanism).
counters/invoices: { year, seq } — incremented inside the same transaction.
users/{uid}: role ('admin' | 'staff'), name. Role is ALSO set as a Firebase Auth custom claim; security rules check the claim.
banners/{id}: admin-managed homepage poster carousel slides (imageUrl, imageUrlMobile, altText, linkUrl, order, isActive, buttonEnabled, buttonLabel, buttonLink, buttonPosition ('bottom-center' | 'bottom-left' | 'center')) — public read of active banners, writes via /api/admin/banners. The CTA button is independent of the slide's own linkUrl (the whole poster can link one place while the button jumps elsewhere) and is rendered as a sibling element over the slide (never nested inside its <Link>), so a click on the button can never double-trigger the slide's own link.
combos/{id}: admin-managed bundle offers shown on /offers and as POS quick-add tiles — title, slug, description, imageUrl, imageUrlMobile, comboPriceInr (the fixed price charged, never the sum of components), originalPriceInr (sum of included/eligible variants' regular prices, computed server-side at save time for the strike-through/savings display only), type ('fixed' | 'choose-any'), items[] ('fixed' only — {productId, variantId, productName, variantLabel, qty}, empty for choose-any), chooseCount (choose-any only, null for fixed), eligibleVariants[] (choose-any only — {productId, variantId, productName, variantLabel}, empty for fixed), isActive, order, validFrom/validUntil (optional Timestamps — see lib/combos.ts's isComboCurrentlyValid), badgeText (optional, e.g. "Save ₹500"), createdAt, updatedAt. Public read of active combos, writes via /api/admin/combos/* (which re-derives every product/variant name, label, and price fresh from live product data server-side — client-submitted snapshots are only used for the admin form's live preview, never trusted). lib/combos.ts's isComboFulfillable does a lightweight stock check (exact per-product ml aggregation for 'fixed'; an optimistic independent-capacity check for 'choose-any', since true joint feasibility across several eligible variants sharing one product's pool is a bin-packing problem not worth solving client-side) — used to hide/disable combos on /offers and POS whose components can't currently be made; recordSale's transaction is the actual authority at purchase time regardless.
siteContent/{id}: admin-editable homepage content blocks, one fixed doc per section, each with its own shape (per-doc-ref converter, not collection-level) — public read, writes via /api/admin/site-content/*. siteContent/giftSection (imageUrl, imageUrlMobile, heading, body, buttonLabel) backs the "Gift a Perfume" section and falls back to hardcoded defaults (lib/store/gift-section-defaults.ts) when the doc doesn't exist yet. siteContent/ourStory (oilCardImageUrl, oilCardImageUrlMobile, sprayCardImageUrl, sprayCardImageUrlMobile, all nullable) backs the two Our Story card images on the homepage and falls back to an icon placeholder per card (matching ProductImage's no-photo treatment) when a field is unset — there's no real product photography in this catalog yet, so this is intentionally not seeded with default photos.
Gifting: a cart line becomes a gift via the "Send as Gift" dialog (recipient name, message ≤200 chars, optional sender name, gift-wrap toggle) captured client-side in lib/cart/types.ts's CartItem.gift; two lines of the same product+variant no longer merge if either is a gift (each gift line is independent, keyed by CartItem.lineId, since they can carry different messages). At checkout, gift items can optionally ship to a separate giftShippingAddress and set the sale-level hidePrices flag. POS has a simpler per-bill-line "Gift wrap" toggle (no recipient/message/address) that still sets isGift+giftWrap on that line. Gifting is PURELY presentation/packing metadata — it does not change stock/oil logic at all; recordSale's stock-check/decrement is unaffected (aggregated per productId+variantId regardless of gift status) and just carries the gift fields through onto each SaleItem unchanged.
Combo offers: a cart/bill combo line is ONE line (lib/cart/types.ts's CartItem.combo / lib/pos/types.ts's BillLine.combo) carrying comboId, comboTitle, its resolved components (for display), and — for 'choose-any' — the customer's flat `selections` (length === chooseCount, repeats allowed); combo lines never merge with each other (like gift lines, always a fresh cart lineId; POS keys a combo bill line by `${comboId}:combo` for 'fixed' or `${comboId}:combo:<hash of picks>` for 'choose-any', so a repeated identical pick still increments in place while a different pick stays separate). The price shown and charged is always comboPriceInr × qty, never a sum of components. At checkout/POS-sale time, the client sends only {kind:"combo", comboId, qty, selections} — never a price or component list — and recordSale/create-order/pos-sale all independently re-read the live combo doc to expand it into its components and price authoritatively.
Critical business rules
recordSale(...) lives in server code (lib/) using firebase-admin and a Firestore transaction: read all product docs, any referenced combo docs, and the invoice counter first (all reads before writes, per Firestore rules). Each input item is either a 'product' line (as before) or a 'combo' line (comboId + qty + choose-any selections); combo lines are expanded — inside the transaction, from the live combo doc, never trusting the client — into their underlying (productId, variantId, qty) draws, which are merged into the SAME per-product-variant aggregation as direct product items, so a fragrance bought both directly and via a combo in one sale nets against its one shared oil pool correctly. Sum ml needed per PRODUCT (qty * oilMlPerUnit across every draw of that product in the sale, direct or combo-sourced), verify oilStockMl >= ml needed for every product (throw if not — overselling must be impossible, and a combo whose components can't be made rejects the whole sale), then deduct oilStockMl once per product, write one stockMovement per underlying (productId, variantId) draw (in ml, negative, with variantId + variantLabel — a combo line writes one movement PER COMPONENT, noted "Combo: <title>", so the audit trail stays itemized per fragrance even though it's one SaleItem), increment the invoice counter, and create the sale doc. A combo produces exactly ONE SaleItem per cart/bill line (never one per component) with unitPrice/lineTotal = comboPriceInr × qty, comboId/comboTitle set, and comboComponents holding the expanded per-fragrance breakdown (each with its own oilMlUsed, already totalled across the line's qty) — reports (lib/admin/salesAggregation.ts's effectiveOilLines) expand comboComponents back out so oil-used-by-product stays accurate. All in ONE transaction. Reports/Dashboard read the oilMlUsed snapshots; sales predating this field fall back to their stockMovements, and a one-time script (scripts/backfill-sale-oil-used.ts) backfilled existing sales. saleItems are built 1:1 from the input items array (never from the aggregated stock-check map), so two lines of the same variant — e.g. one gift, one not — stay as separate line items instead of collapsing into one.
Online: recordSale runs ONLY after Razorpay signature verification server-side. Razorpay webhook route as backup confirmation.
Offline POS: recordSale runs when staff presses "Complete Bill".
ALL writes go through Next.js API routes using firebase-admin (which bypasses security rules). Firestore security rules therefore DENY all client writes; clients may read: active products (public), and sales/stockMovements/users only with admin or staff custom claims.
Secrets (service account JSON, Razorpay secret, webhook secret) are server-side env vars only. Client gets only NEXT_PUBLIC_ Firebase config.
Admin dashboard uses Firestore onSnapshot for live updates.
Maintain firestore.rules and firestore.indexes.json in the repo and deploy them (via the Firebase MCP or firebase CLI) whenever queries change.
