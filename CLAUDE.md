Project: KISWA — Attar / Perfume Store

Production e-commerce + offline POS billing + unified admin panel. Currency: INR (₹). Market: India. Mobile-first. Backend: Firebase.

Three apps in one Next.js project
Storefront (public, route group (store)): luxury feel, dark + gold theme, smooth Framer Motion animations, fast, SEO-friendly.
POS at /pos (staff login): fast tablet/phone billing screen for the physical shop. Big touch targets, minimal taps per bill.
Admin at /admin (admin login): dashboard, products, stock, sales, reports, WhatsApp Orders across BOTH channels.
Inventory model: TWO product types, TWO stock units
products/{id}.productType discriminates 'attar' (our own line, BULK OIL) vs 'imported' (ready-made bottles bought in and resold, UNIT stock) — see lib/firestore/types.ts's ProductDoc = AttarProductDoc | ImportedProductDoc. Attar: every variant of a fragrance (every oil size AND every spray size) is bottled from that fragrance's single shared attar oil pool — there is no independent stock per bottle size. Each attar product has ONE oilStockMl (decimals allowed) and one lowStockThresholdMl (default 10). Each variant has oilMlPerUnit: how many ml of that shared pool one unit of that variant consumes. Defaults: Oil 3ml=3, Oil 6ml=6, Oil 12ml=12, Spray 20ml=2.4, Spray 50ml=6, Spray 100ml=12 — editable per variant in admin. A variant is purchasable only while oilStockMl >= its oilMlPerUnit; the max qty addable (storefront cart or POS bill) is floor(remaining oilStockMl / oilMlPerUnit), where "remaining" nets out oil already committed to OTHER lines of the same product in that same cart/bill (they all draw from one pool). Imported: ONE priceInr, ONE mrpInr, ONE sizeLabel (free text, e.g. "100ml EDP"), no variants array, no oil pool at all — stock is unitStock (whole bottles) and lowStockThresholdUnits (default 2), changed only via the same stockIn/stockAdjust/recordSale transactions as attar, just unit-based. lib/products.ts's IMPORTED_VARIANT_ID ("unit") is the placeholder variantId used everywhere a (productId, variantId) pair is needed for an imported line — cart, POS bill, SaleItem, combo items/eligibleVariants — mirroring how combo lines already use the literal "combo"; it has no real variant entity behind it (an imported product's stockMovements always use variantId: null, variantLabel: <sizeLabel> instead, since there's nothing variant-specific to name).
Firestore data model
products/{id} (id = slug): productType ('attar' | 'imported') plus shared fields name, slug, description, notes (fragrance notes), category, imageUrls[], isActive, createdAt. Attar adds: oilStockMl, lowStockThresholdMl, variants[] (embedded array: variantId, type ('oil' | 'spray'), sizeMl, priceInr, mrpInr, oilMlPerUnit, isActive) — every fragrance has exactly six variants: Oil 3ml/6ml/12ml, Spray 20ml/50ml/100ml. Imported adds: priceInr, mrpInr, sizeLabel, brand (nullable), unitStock, lowStockThresholdUnits, featuredOnHome (bool, admin opt-in to appear in the homepage "Imported Perfumes" section — most imported products are NOT featured by default), featuredOrder (nullable number — lower shows first among featured imported products; unset falls back to newest first; meaningless when featuredOnHome is false). `oilStockMl`/`unitStock` is the ONLY stock number for the product — it may ONLY be changed inside the recordSale/stockIn/stockAdjust transactions below, never edited directly. A product's type is fixed at creation (app/api/admin/products/[id]/route.ts's PATCH rejects any attempt to change it).
stockMovements/{id}: productId, productName, variantId (nullable — set only for sale-driven line items of an ATTAR product; null for product-level Stock In/Adjustment/Set-exact-stock, and always null for imported products, which have no variant entity), variantLabel (nullable, snapshot like "Oil 3ml" for attar or the product's sizeLabel for imported), mlChange (+/- quantity change, in `unit`), unit ('ml' | 'unit' — missing on movements recorded before this field existed, always treat missing as 'ml'), reason ('opening_stock' | 'purchase' | 'online_sale' | 'offline_sale' | 'adjustment' | 'return'), referenceId (saleId if any), note, createdAt. Every stock change writes a movement — this is the audit trail.
sales/{id}: channel ('online' | 'offline'), invoiceNo (unique, 'KSW-YYYY-NNNN'), customerName, customerPhone, items[] (embedded array: productId, productName, variantId, sizeMl, unitPrice, qty, lineTotal, oilMlUsed — oilMlPerUnit*qty snapshotted at sale time for attar, always 0 for imported (which never touches the oil pool, so it naturally can't distort oil-usage reports without any special-casing) — productType (optional, snapshotted; missing on sales predating this field means 'attar'), sizeLabel (imported only, snapshot of the product's sizeLabel), plus gifting metadata isGift, giftRecipientName, giftMessage, giftSenderName, giftWrap, all optional/false by default, plus combo metadata comboId, comboTitle, comboComponents (optional — set only for combo lines; see Combo offers below; each component also carries its own productType so oil-usage reports can skip imported components)), subtotal, discount, total, totalOilMlUsed (sum of items[].oilMlUsed, snapshotted), paymentMethod ('razorpay' | 'cash' | 'upi' | 'card'), paymentStatus, razorpayOrderId, razorpayPaymentId, orderStatus ('pending' | 'paid' | 'packed' | 'shipped' | 'delivered' | 'cancelled'), shippingAddress (map, online only), createdByUid, createdAt, giftShippingAddress (optional map — line1/line2/city/state/pincode/country plus name/phone for the recipient; set only when a gift item's "deliver to a different address" was chosen at checkout), hidePrices (optional bool, default false — "hide prices in the package" packing instruction, not a technical price-hiding mechanism), customerUid (optional, nullable — uid of the signed-in customer who placed this order; null for POS/offline sales and guest WhatsApp/online orders; see "Customer order history" below), deliveryAddress (optional, nullable — a DeliveryAddressSnapshot, the customer-accounts saved-address shape; separate from shippingAddress, which is the older, narrower Razorpay-checkout-only shape — a given sale populates at most one of the two).
counters/invoices: { year, seq } — incremented inside the same transaction.
users/{uid}: role ('admin' | 'staff'), name. Role is ALSO set as a Firebase Auth custom claim; security rules check the claim.
banners/{id}: admin-managed homepage poster carousel slides — lib/firestore/types.ts's BannerDoc = ImageBannerDoc | ComboBannerDoc, discriminated by bannerType ('image' | 'combo', fixed at creation like productType; banners saved before this field existed have none in Firestore, so every read site treats a missing/non-"combo" bannerType as "image", same pattern as stockMovements' missing `unit`). Image banners (imageUrl, imageUrlMobile, altText, linkUrl, order, isActive, buttonEnabled, buttonLabel, buttonLink, buttonPosition ('bottom-center' | 'bottom-left' | 'center')) are the original poster upload — unchanged. Combo banners (comboId, headlineOverride, buttonLabelOverride, order, isActive) instead reference an existing combo and render a slide generated ENTIRELY from that combo's live data (title/description/image/price/originalPrice/badgeText) — no image upload, no stored price, so editing the combo in admin updates the banner with no re-save; headlineOverride/buttonLabelOverride optionally override the headline text / CTA label (default "Shop This Combo"), and the button always links to that combo's /offers/[slug]. Public read via /api/admin/banners (writes) as before; lib/store/queries.ts's getActiveBanners() is the single place that resolves combo banners against a live combo doc and is also the safety gate — a combo banner is silently dropped from the returned list (never rendered as a broken/dangling slide) if its combo is deleted, inactive, outside its validFrom/validUntil window (both via isComboCurrentlyValid, reused from combos), or currently unfulfillable from stock (via isComboFulfillable) — every exclusion is `console.warn`'d server-side with the specific comboId and reason (deleted / inactive / outside date window / which component is short and by how much, via lib/combos.ts's explainComboUnfulfillable) so a legitimately out-of-stock combo is never mistaken for a rendering bug. If that empties the list, BannerCarousel renders nothing and the page flows up cleanly, same as today. components/admin/banners/banner-table.tsx surfaces that same reason (deleted/inactive/expired/out-of-stock, via the same explainComboUnfulfillable/isComboCurrentlyValid helpers) as a non-blocking warning next to any combo banner that's currently hidden, so the admin can see why it's not live without checking server logs. The CTA button (both banner types) is independent of the slide's own link and is rendered as a sibling element over the slide (never nested inside its <Link>/<a>, since HTML disallows nested links anyway), so a click on the button can never double-trigger the slide's own link.
combos/{id}: admin-managed bundle offers shown on /offers and as POS quick-add tiles — title, slug, description, imageUrl, imageUrlMobile, comboPriceInr (the fixed price charged, never the sum of components), originalPriceInr (sum of included/eligible variants' regular prices, computed server-side at save time for the strike-through/savings display only), type ('fixed' | 'choose-any'), items[] ('fixed' only — {productId, variantId, productName, variantLabel, qty}, empty for choose-any), chooseCount (choose-any only, null for fixed), eligibleVariants[] (choose-any only — {productId, variantId, productName, variantLabel}, empty for fixed), isActive, order, validFrom/validUntil (optional Timestamps — see lib/combos.ts's isComboCurrentlyValid), badgeText (optional, e.g. "Save ₹500"), createdAt, updatedAt. Public read of active combos, writes via /api/admin/combos/* (which re-derives every product/variant name, label, and price fresh from live product data server-side — client-submitted snapshots are only used for the admin form's live preview, never trusted). lib/combos.ts's isComboFulfillable does a lightweight stock check (exact per-product ml aggregation for 'fixed'; an optimistic independent-capacity check for 'choose-any', since true joint feasibility across several eligible variants sharing one product's pool is a bin-packing problem not worth solving client-side) — used to hide/disable combos on /offers and POS whose components can't currently be made; recordSale's transaction is the actual authority at purchase time regardless.
siteContent/{id}: admin-editable homepage content blocks, one fixed doc per section, each with its own shape (per-doc-ref converter, not collection-level) — public read, writes via /api/admin/site-content/*. siteContent/giftSection (imageUrl, imageUrlMobile, heading, body, buttonLabel) backs the "Gift a Perfume" section and falls back to hardcoded defaults (lib/store/gift-section-defaults.ts) when the doc doesn't exist yet. siteContent/ourStory (oilCardImageUrl, oilCardImageUrlMobile, sprayCardImageUrl, sprayCardImageUrlMobile, all nullable) backs the two Our Story card images on the homepage and falls back to an icon placeholder per card (matching ProductImage's no-photo treatment) when a field is unset — there's no real product photography in this catalog yet, so this is intentionally not seeded with default photos. siteContent/announcementBar (isEnabled, messages[], backgroundColor, textColor, speed ('slow' | 'normal' | 'fast'), linkUrl nullable, validFrom/validUntil nullable Timestamps) backs the scrolling strip above the header, shown sitewide (mounted in the (store) layout, not homepage-only). lib/store/announcement.ts's isAnnouncementBarRenderable is the single place that decides whether it renders at all — disabled, zero messages, or outside its optional validFrom/validUntil window (null on either side = unbounded, not expired) all mean "nothing at all", never an empty strip, and the same helper's per-condition logic is mirrored (not re-derived) by the admin form's live "why is this hidden" note, the same silent-vs-loud philosophy as the combo banner warning. lib/store/queries.ts's getAnnouncementBar() runs server-side in the (store) layout (not client-fetched), so there's never a flash of stale text; components/store/announcement-bar-visual.tsx is the actual marquee visual (seamless two-track loop, messages joined with a fixed gold dot, speed mapped to animation-duration) shared verbatim by the real storefront bar and the admin form's live preview, so the preview is never an approximation. Messages/colors/speed/link/dates are all admin-editable from Home Sections; backgroundColor/textColor default to the theme's maroon/cream (#4a1220 / #f6f1e6). Seeded once via `npm run seed:announcement-bar` (idempotent — no-ops if the doc already exists) to carry over the previous hardcoded marquee text when this became Firestore-backed, so nothing regressed on that deploy. siteContent/importedSection (isEnabled, heading, subline) controls only the copy and on/off switch of the homepage's last section, "Imported Perfumes" (components/store/imported-perfumes-section.tsx) — it does NOT list which products appear; that's queried live via lib/store/queries.ts's getFeaturedImportedProducts(), which reads active, in-stock (unitStock > 0) imported products with featuredOnHome true, ordered by featuredOrder (nulls falling back to newest-first), capped at 8. The section renders nothing at all (no heading, no gap) if disabled, if the doc doesn't exist yet (falls back to isEnabled: true with hardcoded default heading/subline in lib/store/imported-section-defaults.ts, same pattern as giftSection), or if there are currently zero qualifying products — so a fully unconfigured store or one with no featured imported products never shows an empty section. Cards reuse the shared ProductCard/FocusRail/TiltCard components (same tilt-on-hover treatment, touch-safe) — ProductCard shows brand (imported only, if set) and sizeLabel in place of fragrance notes when productType is 'imported', and the price omits the "From ₹" prefix since imported products have one price, not a range. siteContent/siteSettings (brandName, tagline, shortDescription, whatsappNumber, instagramUrl, facebookUrl, youtubeUrl, email, phone, addressLine, mapUrl — all nullable except the first four) is the single source of truth for brand identity and every social/contact link sitewide, edited from Home Sections > Brand Settings. lib/store/queries.ts's getSiteSettings() never returns null (unlike the other siteContent sections) — brandName/tagline/shortDescription/whatsappNumber always resolve to something usable (hardcoded defaults in lib/store/site-settings-defaults.ts before the doc is seeded, real Firestore data after — seeded once via `npm run seed:site-settings`), since page metadata and the WhatsApp ordering flows need them to function; every other field is normalized to null when unset (including an admin-cleared empty string) so every read site does one `if (settings.x)` check and renders nothing at all for it — no icon, no blank line, no href="#". lib/store/site-settings-context.tsx's SiteSettingsProvider (mounted once in the (store) layout, fed by the one server-side getSiteSettings() call) makes this available to any client component via useSiteSettings() without prop-drilling — consumed by the footer, mobile nav drawer (components/store/menu-drawer.tsx), the floating WhatsApp button, and the WhatsApp "order" links on the product page and cart drawer (lib/whatsapp.ts's buildWhatsAppUrl takes the number as a parameter, defaulting to the env var only as a last resort). components/store/contact-block.tsx's ContactBlock (address + SocialIconsRow + mailto/tel) and its inner SocialIconsRow (just the WhatsApp/Instagram/Facebook/YouTube icon buttons, used standalone by the compact mobile drawer) are shared verbatim by the real footer and the admin form's live preview, the same "the preview is never an approximation" pattern as the announcement bar. The admin form (components/admin/home-sections/brand-settings-form.tsx) validates https:// URLs and email format, and flags a pasted social URL containing known tracking query params (utm_*, fbclid, igshid, gclid, etc.) with a one-click "Strip them" button that removes only those specific keys, never the whole query string. The root layout's generateMetadata (app/layout.tsx, necessarily async to read getSiteSettings()) builds the sitewide title template (`%s — ${brandName}`, default `${brandName} — ${tagline}`), meta description, and OpenGraph/Twitter tags from siteSettings — every page-level metadata.title across the app was correspondingly trimmed to drop its own hardcoded "— KISWA" suffix (e.g. "Shop", not "Shop — KISWA") so the template supplies it exactly once. The (store) layout also emits a JSON-LD Organization `<script>` (name, email, Instagram URL as sameAs, and a PostalAddress hardcoded to Ponoor/Kerala/IN per the business's actual location) — there's no real brand logo asset in this project (only the stock Next.js favicon), so `logo` is deliberately omitted rather than pointing structured data at a placeholder image; add a real logo file and wire it in if one becomes available.
Image uploads: ALL admin image uploads (banners, combos, product galleries) share one mechanism — lib/server/imageStorage.ts's saveUploadedImage/deleteUploadedImage write to Firebase Storage via firebase-admin (NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET), returning a permanent public download-URL (Firebase's own getDownloadURL() shape, with a per-object access token embedded in the object's metadata) — this bypasses storage.rules entirely (same principle as every Firestore write in this app going through firebase-admin), so storage.rules stays deny-all with nothing to weaken; a raw storage.googleapis.com/<bucket>/<path> URL would NOT work here (that's governed by separate GCS bucket ACLs, not these rules — a common mix-up). This replaced an earlier local-filesystem approach (writing to /public/<subdir> on the Node server's own disk) that doesn't survive on serverless/edge hosts like Vercel, whose filesystem is read-only at runtime and freshly rebuilt on every deploy. next.config.ts's images.remotePatterns allowlists exactly this one bucket's download-URL host+path (nothing else) so next/image's optimizer can use it; components/store/product-image.tsx treats a same-origin "/..." path OR a URL under that same allowlisted prefix as "ours" (next/image), anything else (a pasted external supplier URL) as a plain `<img>` — deliberately never allowlisting arbitrary external hosts, which would let the image optimizer fetch any URL an admin pastes in. lib/server/bannerImages.ts (banners + combos, subdir "banners") and lib/server/productImages.ts (product galleries, subdir "products") are thin per-feature wrappers around it. Products' imageUrls[] can mix uploaded URLs and pasted external https:// URLs in any order — components/admin/products/image-uploader.tsx is the shared multi-image gallery editor (drag-and-drop or click-to-browse, client-side resized to max 1600px on the long edge before upload via canvas, one POST to /api/admin/products/upload-image per file so each thumbnail shows its own progress, drag-to-reorder, delete, plus a "paste an image URL" fallback for supplier links) — first entry is the primary/listing image everywhere (admin table, storefront gallery/card, /shop, POS). The product POST/PATCH routes only ever receive the final imageUrls[] array (never a file), and PATCH diffs old vs new on save to delete any now-orphaned uploaded file (pasted external URLs are never touched, matched against our own bucket's URL prefix).
Gifting: a cart line becomes a gift via the "Send as Gift" dialog (recipient name, message ≤200 chars, optional sender name, gift-wrap toggle) captured client-side in lib/cart/types.ts's CartItem.gift; two lines of the same product+variant no longer merge if either is a gift (each gift line is independent, keyed by CartItem.lineId, since they can carry different messages). At checkout, gift items can optionally ship to a separate giftShippingAddress and set the sale-level hidePrices flag. POS has a simpler per-bill-line "Gift wrap" toggle (no recipient/message/address) that still sets isGift+giftWrap on that line. Gifting is PURELY presentation/packing metadata — it does not change stock/oil logic at all; recordSale's stock-check/decrement is unaffected (aggregated per productId+variantId regardless of gift status) and just carries the gift fields through onto each SaleItem unchanged.
WhatsApp ordering: lib/whatsapp.ts is the single source for the WhatsApp number (NEXT_PUBLIC_WHATSAPP_NUMBER, default 919995778963) and for building wa.me links/messages — read it everywhere rather than hardcoding the number. Three entry points: a per-product "Order on WhatsApp" button on the product page (message reflects the currently selected variant + qty, disabled exactly when Add to Bag would be, i.e. maxQty <= 0), an "Order this cart on WhatsApp"/"Order on WhatsApp" link in the cart drawer (every line + line total, truncated to 10 lines then "…and N more items", then the order total — buildCartOrderMessage additionally itemizes a combo line's components and a gift line's recipient/message/wrap choice underneath it, so the message alone is complete enough to bill from), and a floating round button on every storefront page for a generic enquiry (mounted in app/(store)/layout.tsx, so it's absent from /pos and /admin by construction). This is PURELY an enquiry handoff to a human — it never calls recordSale, never touches stock/oilStockMl, and creates no sale/order doc; staff key the confirmed order into POS or (for a channel-appropriate 'online' sale with no physical counter) Admin's WhatsApp Orders screen once confirmed over chat.
Customer accounts: a storefront identity system entirely separate from the admin/staff Firebase Auth users described above — customers/{uid} (lib/firestore/types.ts's CustomerDoc: name, email, phone, createdAt, lastLoginAt, marketingOptIn) get NO custom claim at all, so every existing admin/staff role check (allowlist-based: `role === 'admin' | 'staff'` in both /admin's and /pos's session gates and firestore.rules' hasRole()) already rejects a customer with zero special-casing — a customer's Firebase Auth ID token simply has no `role` claim to match. Sign-in methods: email/password and Google (signInWithPopup), both client-side via lib/firebase/client.ts's `auth`, same pattern as the existing admin LoginForm; phone/OTP was deliberately skipped (would need the Phone provider enabled in Firebase Console, a reCAPTCHA widget, and a separate OTP-confirmation UI step — meaningfully more surface than email/Google, not "straightforward"). Sessions use a SEPARATE httpOnly cookie (lib/server/customerSessionCookie.ts's `__customer_session`, 14 days — Firebase's own hard cap on session-cookie `expiresIn` — vs admin/staff's `__session` at 5 days) with its own verify path (lib/server/getCustomerSession.ts) — deliberately never sharing a cookie name with lib/server/sessionCookie.ts so a customer and a staff/admin signed in on the same browser can never clobber each other's session, and so /admin and /pos's gates are structurally unaffected by any of this. app/api/account/session (login + Google — client already holds a Firebase idToken, upserts via lib/server/customers.ts's touchCustomerOnLogin) and app/api/account/signup (the ONE exception to "client authenticates with Firebase directly, server only mints the cookie" — this route creates the Firebase Auth user itself via adminAuth.createUser after Zod-validating the raw password, which is the only way the password policy is actually enforced rather than just suggested: a client-side createUserWithEmailAndPassword call would mean the raw password never crosses the server boundary at all. Returns a custom token — session cookies can only be minted from a real ID token, not a custom token — which the client exchanges via signInWithCustomToken, then calls /api/account/session like any other login to establish the actual session) both independently re-verify the caller server-side and HARD REJECT (403) if an existing account carries an admin/staff role claim, before creating anything — defense in depth on top of verifyCustomerSessionCookie() also refusing to trust a role claim even inside a customer session cookie. Pages: /account/login, /account/signup, /account/forgot-password (all standalone/full-screen like the existing /login, not nested in the (store) layout) plus, nested in the (store) layout and sharing components/account/account-nav.tsx's Profile/Addresses/My Orders tabs, /(store)/account (a dashboard: greeting, quick-link cards to Addresses/Orders, the profile-edit section, and a password-change section — components/account/account-password-form.tsx branches on the signed-in Firebase user's own providerData: email/password users get a current-password + new-password form using reauthenticateWithCredential then updatePassword client-side, Google-only users get a message pointing them at their Google Account instead, since there's no KISWA password to change), /(store)/account/addresses (add/edit/delete/set-default, see below), and /(store)/account/orders (a placeholder — sales aren't linked to a customer uid at checkout in this pass, so this intentionally does NOT touch the ordering/checkout flow; it just points back to WhatsApp). lib/auth/safeRedirect.ts's sanitizeRedirect() is the one place every `?redirect=` param is validated (must be a same-origin path, rejecting absolute/protocol-relative URLs) before use, shared by all three auth pages and the header's login link. components/store/account-menu.tsx (the header icon next to search/cart) deliberately does NOT receive the customer session as a server-rendered prop from app/(store)/layout.tsx — reading cookies() there would force that layout's `cookies()` dynamic-API cost onto EVERY page beneath it, including currently-static/ISR pages like / and /offers, undoing the static-rendering behavior this codebase depends on. Instead it self-fetches GET /api/account/me on mount, trading a brief post-paint resolve for keeping the rest of the storefront static. Rate-limited (lib/server/rateLimit.ts, same per-IP pattern as /api/auth/session): signup, session, forgot-password, and profile routes. /api/account/forgot-password exists purely as a rate-limit + validation gate — actually SENDING the reset email is Firebase's own client-SDK sendPasswordResetEmail() (there's no server-side mail infra in this app, and the Admin SDK's generatePasswordResetLink only generates a link, it doesn't deliver one); the client always shows the same generic "if an account exists…" message regardless of outcome, silently swallowing auth/user-not-found, so existence is never leaked at either layer. Password policy (lib/auth/customerValidation.ts, Zod, enforced both client- and server-side): minimum 8 characters with at least one letter and one number, stricter than Firebase's own 6-character default. This step deliberately does NOT change the ordering/checkout flow — guests still browse and order on WhatsApp exactly as before; a signed-in customer isn't yet threaded through checkout, create-order, or recordSale. Saved delivery addresses live at customers/{uid}/addresses/{id} (lib/firestore/types.ts's AddressDoc: label, fullName, phone, line1, line2, city, district, state, pincode, landmark, isDefault, createdAt, updatedAt — phone/pincode validated against the same 10-digit-Indian-mobile/6-digit-PIN shape as checkout-form.tsx's own regexes, not the looser international one on the profile's own phone field). firestore.rules' customers/{uid} match block (and its nested addresses match) is `allow read, write: if request.auth.uid == uid` — the ONE deliberate exception in this codebase to "all writes go through firebase-admin, rules stay deny-all": the app's own UI still writes exclusively through /api/account/addresses/* (firebase-admin, Zod-validated, uid always taken from the verified session cookie, never client input), but the rule itself is written to be the real security boundary a raw/future direct-SDK write would still have to pass, not merely a UI convenience — this is also why the request explicitly asked to verify isolation by querying Firestore directly rather than just through the UI. lib/server/customerAddresses.ts is the sole place the "exactly one default address at a time" invariant is enforced (Firestore rules can't express a cross-document constraint like that): creating a customer's first address always forces isDefault true regardless of what was submitted; setting any other address default unsets the previous one in the same transaction; deleting the current default promotes the next-most-recent remaining address if any exist. All three (create/update/delete) read every sibling address before writing anything, since Firestore transactions require all reads before any write.
Customer order history: sales/{id}.customerUid links an order back to customers/{uid} — set automatically (never client-supplied) wherever recordSale is called with a signed-in customer's uid: /api/checkout/create-order → lib/server/finalizeOnlineOrder.ts (a logged-in customer's Razorpay checkout), and the new /api/admin/whatsapp-orders/[id]/convert (see below). POS sales and guest checkouts/WhatsApp orders always have customerUid null — this pass adds zero new code paths to recordSale itself (lib/server/recordSale.ts only gained customerUid/deliveryAddress as plain passthrough fields with defaults of null; the transaction's stock/oil/invoice-numbering logic is untouched). /(store)/account/orders (lib/server/customerOrders.ts's getCustomerOrders, needing the sales(customerUid ASC, createdAt DESC) composite index) lists that customer's orders newest-first with an empty state; /(store)/account/orders/[id] (getCustomerOrder) shows full detail via components/store/order-invoice.tsx's OrderInvoice (shared verbatim with the Razorpay checkout success page, including its print/"Download bill" treatment — same #order-invoice print CSS in globals.css) — getCustomerOrder returns null both when the id doesn't exist AND when it belongs to someone else, so the page 404s identically either way rather than leaking existence. OrderInvoice's item labeling was also fixed while touching this (it previously guessed variant labels from `variantId.startsWith("oil")`, which mislabeled every combo and imported line — a real, pre-existing bug on the Razorpay success page too, just never noticed since imported/combo online orders are rare); it now uses lib/admin/salesAggregation.ts's itemVariantLabel plus the same comboComponents-first branching as the admin Sale detail modal. firestore.rules' sales/{saleId} now additionally allows a signed-in customer to read a sale where resource.data.customerUid == their own uid (admin retains full read); customers/{uid} additionally allows hasRole('admin') read (write stays self-only) so Admin > Sales' linked-customer block and the new /admin/customers/[uid] profile page (name/email/phone, lifetime order count + total, full order list, all read via firebase-admin server-side — no client Firestore calls needed there) can look up an arbitrary customer. Critical business rules
recordSale(...) lives in server code (lib/) using firebase-admin and a Firestore transaction: read all product docs, any referenced combo docs, and the invoice counter first (all reads before writes, per Firestore rules). Each input item is either a 'product' line (as before) or a 'combo' line (comboId + qty + choose-any selections); combo lines are expanded — inside the transaction, from the live combo doc, never trusting the client — into their underlying (productId, variantId, qty) draws, which are merged into the SAME per-product-variant aggregation as direct product items, so a fragrance bought both directly and via a combo in one sale nets against its one shared pool correctly (oilStockMl for attar, unitStock for imported — a combo can mix either). lib/server/productLookup.ts's aggregateProductNeeds validates every draw (active variant + enough oilStockMl for attar; active product + enough unitStock for imported — imported has no variant-level isActive, so the product's own isActive gates it) and returns the ml/units needed per product (throw if insufficient — overselling must be impossible for both stock models, and a combo whose components can't be made rejects the whole sale), then recordSale deducts oilStockMl or unitStock once per product accordingly, writes one stockMovement per underlying (productId, variantId) draw (attar: ml, negative, with the real variantId + variantLabel; imported: whole units, negative, variantId null + variantLabel = the product's sizeLabel — a combo line writes one movement PER COMPONENT, noted "Combo: <title>", so the audit trail stays itemized per fragrance/product even though it's one SaleItem), increments the invoice counter, and creates the sale doc. A combo produces exactly ONE SaleItem per cart/bill line (never one per component) with unitPrice/lineTotal = comboPriceInr × qty, comboId/comboTitle set, and comboComponents holding the expanded per-component breakdown (each with its own oilMlUsed — 0 for imported components — and productType, already totalled across the line's qty) — reports (lib/admin/salesAggregation.ts's effectiveOilLines) expand comboComponents back out so oil-used-by-product stays accurate and attar-only (imported items/components are skipped, not just zero-valued, so they don't add noisy 0ml rows). All in ONE transaction. Reports/Dashboard read the oilMlUsed snapshots; sales predating this field fall back to their stockMovements, and a one-time script (scripts/backfill-sale-oil-used.ts) backfilled existing sales. saleItems are built 1:1 from the input items array (never from the aggregated stock-check map), so two lines of the same variant — e.g. one gift, one not — stay as separate line items instead of collapsing into one. create-order and pos/sale independently re-derive price via lib/server/productLookup.ts's livePriceForVariant (never trusting the client) — same attar/imported branching, but stock sufficiency is only pre-checked in create-order (a faster UX failure before a Razorpay order exists); recordSale's own transaction is the actual authority in both channels regardless.

ALL writes go through Next.js API routes using firebase-admin (which bypasses security rules). Firestore security rules therefore DENY all client writes; clients may read: active products (public), and sales/stockMovements/users only with admin or staff custom claims. lib/firebase/admin.ts's adminAuth/adminDb are lazily constructed behind a Proxy (see that file's own comment) rather than eagerly at module scope — a real, reproduced bug: Next's build evaluates every route/layout module's top-level imports (not just the ones a given request touches), and lib/store/queries.ts (imported by both the root layout and the (store) layout, i.e. every page including /_not-found) reaches this file transitively via lib/firestore/admin-collections.ts, so an eager `cert(loadServiceAccount())` throwing at import time from a missing/misconfigured FIREBASE_SERVICE_ACCOUNT_KEY (e.g. a Vercel env var typo) crashed the entire build, uncatchable by any downstream try/catch. The lazy Proxy defers that throw to first real property access, which happens inside whatever async function is calling it (see queries.ts's safeRead()) and can therefore actually be caught. Never reintroduce an eager `initializeApp({credential: cert(...)})` at module scope anywhere.
