Project: KISWA — Attar / Perfume Store

Production e-commerce + offline POS billing + unified admin panel. Currency: INR (₹). Market: India. Mobile-first. Backend: Firebase.

Three apps in one Next.js project
Storefront (public, route group (store)): luxury feel, dark + gold theme, smooth Framer Motion animations, fast, SEO-friendly.
POS at /pos (staff login): fast tablet/phone billing screen for the physical shop. Big touch targets, minimal taps per bill.
Admin at /admin (admin login): dashboard, products, stock, sales, reports across BOTH channels.
Inventory model: TWO product types, TWO stock units
products/{id}.productType discriminates 'attar' (our own line, BULK OIL) vs 'imported' (ready-made bottles bought in and resold, UNIT stock) — see lib/firestore/types.ts's ProductDoc = AttarProductDoc | ImportedProductDoc. Attar: every variant of a fragrance (every oil size AND every spray size) is bottled from that fragrance's single shared attar oil pool — there is no independent stock per bottle size. Each attar product has ONE oilStockMl (decimals allowed) and one lowStockThresholdMl (default 10). Each variant has oilMlPerUnit: how many ml of that shared pool one unit of that variant consumes. Defaults: Oil 3ml=3, Oil 6ml=6, Oil 12ml=12, Spray 20ml=2.4, Spray 50ml=6, Spray 100ml=12 — editable per variant in admin. A variant is purchasable only while oilStockMl >= its oilMlPerUnit; the max qty addable (storefront cart or POS bill) is floor(remaining oilStockMl / oilMlPerUnit), where "remaining" nets out oil already committed to OTHER lines of the same product in that same cart/bill (they all draw from one pool). Imported: ONE priceInr, ONE mrpInr, ONE sizeLabel (free text, e.g. "100ml EDP"), no variants array, no oil pool at all — stock is unitStock (whole bottles) and lowStockThresholdUnits (default 2), changed only via the same stockIn/stockAdjust/recordSale transactions as attar, just unit-based. lib/products.ts's IMPORTED_VARIANT_ID ("unit") is the placeholder variantId used everywhere a (productId, variantId) pair is needed for an imported line — cart, POS bill, SaleItem, combo items/eligibleVariants — mirroring how combo lines already use the literal "combo"; it has no real variant entity behind it (an imported product's stockMovements always use variantId: null, variantLabel: <sizeLabel> instead, since there's nothing variant-specific to name).
Firestore data model
products/{id} (id = slug): productType ('attar' | 'imported') plus shared fields name, slug, description, notes (fragrance notes), category, imageUrls[], isActive, createdAt. Attar adds: oilStockMl, lowStockThresholdMl, variants[] (embedded array: variantId, type ('oil' | 'spray'), sizeMl, priceInr, mrpInr, oilMlPerUnit, isActive) — every fragrance has exactly six variants: Oil 3ml/6ml/12ml, Spray 20ml/50ml/100ml. Imported adds: priceInr, mrpInr, sizeLabel, brand (nullable), unitStock, lowStockThresholdUnits. `oilStockMl`/`unitStock` is the ONLY stock number for the product — it may ONLY be changed inside the recordSale/stockIn/stockAdjust transactions below, never edited directly. A product's type is fixed at creation (app/api/admin/products/[id]/route.ts's PATCH rejects any attempt to change it).
stockMovements/{id}: productId, productName, variantId (nullable — set only for sale-driven line items of an ATTAR product; null for product-level Stock In/Adjustment/Set-exact-stock, and always null for imported products, which have no variant entity), variantLabel (nullable, snapshot like "Oil 3ml" for attar or the product's sizeLabel for imported), mlChange (+/- quantity change, in `unit`), unit ('ml' | 'unit' — missing on movements recorded before this field existed, always treat missing as 'ml'), reason ('opening_stock' | 'purchase' | 'online_sale' | 'offline_sale' | 'adjustment' | 'return'), referenceId (saleId if any), note, createdAt. Every stock change writes a movement — this is the audit trail.
sales/{id}: channel ('online' | 'offline'), invoiceNo (unique, 'KSW-YYYY-NNNN'), customerName, customerPhone, items[] (embedded array: productId, productName, variantId, sizeMl, unitPrice, qty, lineTotal, oilMlUsed — oilMlPerUnit*qty snapshotted at sale time for attar, always 0 for imported (which never touches the oil pool, so it naturally can't distort oil-usage reports without any special-casing) — productType (optional, snapshotted; missing on sales predating this field means 'attar'), sizeLabel (imported only, snapshot of the product's sizeLabel), plus gifting metadata isGift, giftRecipientName, giftMessage, giftSenderName, giftWrap, all optional/false by default, plus combo metadata comboId, comboTitle, comboComponents (optional — set only for combo lines; see Combo offers below; each component also carries its own productType so oil-usage reports can skip imported components)), subtotal, discount, total, totalOilMlUsed (sum of items[].oilMlUsed, snapshotted), paymentMethod ('razorpay' | 'cash' | 'upi' | 'card'), paymentStatus, razorpayOrderId, razorpayPaymentId, orderStatus ('pending' | 'paid' | 'packed' | 'shipped' | 'delivered' | 'cancelled'), shippingAddress (map, online only), createdByUid, createdAt, giftShippingAddress (optional map — line1/line2/city/state/pincode/country plus name/phone for the recipient; set only when a gift item's "deliver to a different address" was chosen at checkout), hidePrices (optional bool, default false — "hide prices in the package" packing instruction, not a technical price-hiding mechanism).
counters/invoices: { year, seq } — incremented inside the same transaction.
users/{uid}: role ('admin' | 'staff'), name. Role is ALSO set as a Firebase Auth custom claim; security rules check the claim.
banners/{id}: admin-managed homepage poster carousel slides (imageUrl, imageUrlMobile, altText, linkUrl, order, isActive, buttonEnabled, buttonLabel, buttonLink, buttonPosition ('bottom-center' | 'bottom-left' | 'center')) — public read of active banners, writes via /api/admin/banners. The CTA button is independent of the slide's own linkUrl (the whole poster can link one place while the button jumps elsewhere) and is rendered as a sibling element over the slide (never nested inside its <Link>), so a click on the button can never double-trigger the slide's own link.
combos/{id}: admin-managed bundle offers shown on /offers and as POS quick-add tiles — title, slug, description, imageUrl, imageUrlMobile, comboPriceInr (the fixed price charged, never the sum of components), originalPriceInr (sum of included/eligible variants' regular prices, computed server-side at save time for the strike-through/savings display only), type ('fixed' | 'choose-any'), items[] ('fixed' only — {productId, variantId, productName, variantLabel, qty}, empty for choose-any), chooseCount (choose-any only, null for fixed), eligibleVariants[] (choose-any only — {productId, variantId, productName, variantLabel}, empty for fixed), isActive, order, validFrom/validUntil (optional Timestamps — see lib/combos.ts's isComboCurrentlyValid), badgeText (optional, e.g. "Save ₹500"), createdAt, updatedAt. Public read of active combos, writes via /api/admin/combos/* (which re-derives every product/variant name, label, and price fresh from live product data server-side — client-submitted snapshots are only used for the admin form's live preview, never trusted). lib/combos.ts's isComboFulfillable does a lightweight stock check (exact per-product ml aggregation for 'fixed'; an optimistic independent-capacity check for 'choose-any', since true joint feasibility across several eligible variants sharing one product's pool is a bin-packing problem not worth solving client-side) — used to hide/disable combos on /offers and POS whose components can't currently be made; recordSale's transaction is the actual authority at purchase time regardless.
siteContent/{id}: admin-editable homepage content blocks, one fixed doc per section, each with its own shape (per-doc-ref converter, not collection-level) — public read, writes via /api/admin/site-content/*. siteContent/giftSection (imageUrl, imageUrlMobile, heading, body, buttonLabel) backs the "Gift a Perfume" section and falls back to hardcoded defaults (lib/store/gift-section-defaults.ts) when the doc doesn't exist yet. siteContent/ourStory (oilCardImageUrl, oilCardImageUrlMobile, sprayCardImageUrl, sprayCardImageUrlMobile, all nullable) backs the two Our Story card images on the homepage and falls back to an icon placeholder per card (matching ProductImage's no-photo treatment) when a field is unset — there's no real product photography in this catalog yet, so this is intentionally not seeded with default photos.
Image uploads: ALL admin image uploads (banners, combos, product galleries) share one mechanism — lib/server/localImageStorage.ts's saveUploadedImage/deleteUploadedImage write to /public/<subdir> on the Node server's own filesystem, NOT Firebase Storage (this project has no Storage bucket wired up — no storage.rules, no client/admin Storage SDK usage anywhere — see that file's own comment). lib/server/bannerImages.ts (banners + combos, subdir "banners") and lib/server/productImages.ts (product galleries, subdir "products") are thin per-feature wrappers around it. This only persists on a traditional Node server with a writable filesystem; a serverless/edge deploy would need Firebase Storage instead. Products' imageUrls[] can mix uploaded paths (e.g. "/products/<uuid>.jpg") and pasted external https:// URLs in any order — components/admin/products/image-uploader.tsx is the shared multi-image gallery editor (drag-and-drop or click-to-browse, client-side resized to max 1600px on the long edge before upload via canvas, one POST to /api/admin/products/upload-image per file so each thumbnail shows its own progress, drag-to-reorder, delete, plus a "paste an image URL" fallback for supplier links) — first entry is the primary/listing image everywhere (admin table, storefront gallery/card, /shop, POS). The product POST/PATCH routes only ever receive the final imageUrls[] array (never a file), and PATCH diffs old vs new on save to delete any now-orphaned uploaded file (pasted external URLs are never touched, matched by the /products/ prefix).
Gifting: a cart line becomes a gift via the "Send as Gift" dialog (recipient name, message ≤200 chars, optional sender name, gift-wrap toggle) captured client-side in lib/cart/types.ts's CartItem.gift; two lines of the same product+variant no longer merge if either is a gift (each gift line is independent, keyed by CartItem.lineId, since they can carry different messages). At checkout, gift items can optionally ship to a separate giftShippingAddress and set the sale-level hidePrices flag. POS has a simpler per-bill-line "Gift wrap" toggle (no recipient/message/address) that still sets isGift+giftWrap on that line. Gifting is PURELY presentation/packing metadata — it does not change stock/oil logic at all; recordSale's stock-check/decrement is unaffected (aggregated per productId+variantId regardless of gift status) and just carries the gift fields through onto each SaleItem unchanged.
WhatsApp ordering: lib/whatsapp.ts is the single source for the WhatsApp number (NEXT_PUBLIC_WHATSAPP_NUMBER, default 919995778963) and for building wa.me links/messages — read it everywhere rather than hardcoding the number. Three entry points: a per-product "Order on WhatsApp" button on the product page (message reflects the currently selected variant + qty, disabled exactly when Add to Bag would be, i.e. maxQty <= 0), an "Order this cart on WhatsApp" link in the cart drawer (every line + line total, truncated to 10 lines then "…and N more items", then the order total), and a floating round button on every storefront page for a generic enquiry (mounted in app/(store)/layout.tsx, so it's absent from /pos and /admin by construction). This is PURELY an enquiry handoff to a human — it never calls recordSale, never touches stock/oilStockMl, and creates no sale/order doc; staff bill the order manually in POS once confirmed over chat.
Imported perfumes: a browsable third catalog category alongside attar oils/sprays, filtered via /shop?type=imported and the "Imported Perfumes" nav entry (lib/store/categories.ts's free-text `category` field is unrelated — this is a productType filter, like the existing oil/spray type filter). The storefront product page renders components/store/imported-buy-box.tsx instead of variant-selector.tsx when productType is 'imported' — no oil/spray toggle, no size selector, just a qty stepper capped by remaining unitStock and the same Add to Bag / Send as Gift / Order on WhatsApp actions (gifting and WhatsApp ordering are generic over CartItem and need no imported-specific code). Combos can include imported products as fixed items or eligible variants (lib/combos.ts's fulfillability/pricing helpers and lib/products.ts's shared remainingCapacity/livePriceForVariant branch by productType); lib/server/comboFields.ts re-derives an imported component's name/price/sizeLabel from the live product doc exactly like it does for attar variants. POS shows imported products as grid tiles that add directly to the bill on tap (no variant picker sheet), capped and labeled by unitStock. Admin's product create form starts with an Attar/Imported type choice (fixed after creation) that swaps the whole field set; the Stock page, its Stock In/Adjustment/Set-exact-stock forms, and movement history all branch their unit (ml vs whole units, with imported inputs validated as integers) from each product's own productType, and Reports adds a revenue/units table split by product type (attar/imported/combo) alongside the existing attar-only oil-usage tables.
Combo offers: a cart/bill combo line is ONE line (lib/cart/types.ts's CartItem.combo / lib/pos/types.ts's BillLine.combo) carrying comboId, comboTitle, its resolved components (for display), and — for 'choose-any' — the customer's flat `selections` (length === chooseCount, repeats allowed); combo lines never merge with each other (like gift lines, always a fresh cart lineId; POS keys a combo bill line by `${comboId}:combo` for 'fixed' or `${comboId}:combo:<hash of picks>` for 'choose-any', so a repeated identical pick still increments in place while a different pick stays separate). The price shown and charged is always comboPriceInr × qty, never a sum of components. At checkout/POS-sale time, the client sends only {kind:"combo", comboId, qty, selections} — never a price or component list — and recordSale/create-order/pos-sale all independently re-read the live combo doc to expand it into its components and price authoritatively.
Critical business rules
recordSale(...) lives in server code (lib/) using firebase-admin and a Firestore transaction: read all product docs, any referenced combo docs, and the invoice counter first (all reads before writes, per Firestore rules). Each input item is either a 'product' line (as before) or a 'combo' line (comboId + qty + choose-any selections); combo lines are expanded — inside the transaction, from the live combo doc, never trusting the client — into their underlying (productId, variantId, qty) draws, which are merged into the SAME per-product-variant aggregation as direct product items, so a fragrance bought both directly and via a combo in one sale nets against its one shared pool correctly (oilStockMl for attar, unitStock for imported — a combo can mix either). lib/server/productLookup.ts's aggregateProductNeeds validates every draw (active variant + enough oilStockMl for attar; active product + enough unitStock for imported — imported has no variant-level isActive, so the product's own isActive gates it) and returns the ml/units needed per product (throw if insufficient — overselling must be impossible for both stock models, and a combo whose components can't be made rejects the whole sale), then recordSale deducts oilStockMl or unitStock once per product accordingly, writes one stockMovement per underlying (productId, variantId) draw (attar: ml, negative, with the real variantId + variantLabel; imported: whole units, negative, variantId null + variantLabel = the product's sizeLabel — a combo line writes one movement PER COMPONENT, noted "Combo: <title>", so the audit trail stays itemized per fragrance/product even though it's one SaleItem), increments the invoice counter, and creates the sale doc. A combo produces exactly ONE SaleItem per cart/bill line (never one per component) with unitPrice/lineTotal = comboPriceInr × qty, comboId/comboTitle set, and comboComponents holding the expanded per-component breakdown (each with its own oilMlUsed — 0 for imported components — and productType, already totalled across the line's qty) — reports (lib/admin/salesAggregation.ts's effectiveOilLines) expand comboComponents back out so oil-used-by-product stays accurate and attar-only (imported items/components are skipped, not just zero-valued, so they don't add noisy 0ml rows). All in ONE transaction. Reports/Dashboard read the oilMlUsed snapshots; sales predating this field fall back to their stockMovements, and a one-time script (scripts/backfill-sale-oil-used.ts) backfilled existing sales. saleItems are built 1:1 from the input items array (never from the aggregated stock-check map), so two lines of the same variant — e.g. one gift, one not — stay as separate line items instead of collapsing into one. create-order and pos/sale independently re-derive price via lib/server/productLookup.ts's livePriceForVariant (never trusting the client) — same attar/imported branching, but stock sufficiency is only pre-checked in create-order (a faster UX failure before a Razorpay order exists); recordSale's own transaction is the actual authority in both channels regardless.
Online: recordSale runs ONLY after Razorpay signature verification server-side. Razorpay webhook route as backup confirmation.
Offline POS: recordSale runs when staff presses "Complete Bill".
ALL writes go through Next.js API routes using firebase-admin (which bypasses security rules). Firestore security rules therefore DENY all client writes; clients may read: active products (public), and sales/stockMovements/users only with admin or staff custom claims.
Secrets (service account JSON, Razorpay secret, webhook secret) are server-side env vars only. Client gets only NEXT_PUBLIC_ Firebase config.
Admin dashboard uses Firestore onSnapshot for live updates.
Maintain firestore.rules and firestore.indexes.json in the repo and deploy them (via the Firebase MCP or firebase CLI) whenever queries change.
